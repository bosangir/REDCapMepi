02What is REDCap?

A secure web application for building and managing online surveys and databases.

REDCap (Research Electronic Data Capture) is a secure, web-based platform for building and managing online forms, surveys and databases. Researchers can design their own projects without programming.[1] It was created in 2004 at Vanderbilt University to give clinical researchers secure data collection, and the REDCap Consortium was launched in 2006 so that institutions could share and develop the software together.[1] The method behind it was first described by Harris and colleagues in 2009.[3]

How you get it

REDCap is free for non-profit institutions that join the consortium, but it is not open source and not a public website. Each partner institution installs and runs its own REDCap server, with its own login page, rules and support team.[1][4] You therefore always work in your institution's REDCap. This matters for the GDPR: the data stay on a server managed by your institution.

Main features

  • Forms and surveys: data entry forms for staff, and surveys that participants fill in themselves.[2]
  • Online Designer or data dictionary: build forms in the browser, or design them in a spreadsheet and upload it.[2]
  • Audit trail: every change to the data, and who made it, is logged.[2]
  • Multi-site and user management: researchers at several sites work in one project; the project team manages its own users.[2]
  • Branching logic, calculated fields and file uploads.[2]
  • Exports to Excel/CSV, PDF, SPSS, SAS, Stata and R.[2]
  • Mobile app for iOS and Android for offline data collection, and Multi-Language Management for translated forms.[2]
  • Draft Preview Mode: test changes to a live project, including logic and calculations, before submitting them; data entered in preview are not saved.[2]

03Why not a spreadsheet?

An EDC system builds quality and security into data entry.

Many studies still start in Excel. It is easy, but it lets anyone type anything anywhere, keeps no record of who changed what, and is easily emailed or copied to a USB stick. An electronic data capture system such as REDCap prevents most of these problems by design.[9]

04The building blocks of a project

Six words you need to know before you open REDCap.

Record
One participant (or one unit of observation), identified by the first field, usually record_id.
Instrument
A form or a survey: a group of related questions, such as "Enrolment" or "Lab results".
Field
One variable or question, such as weight_kg.
Event
A time point in a longitudinal study, such as Baseline or Month 2.
Arm
A study group with its own schedule of events, for example the two arms of a trial.
DAG
Data Access Group: a group of users, usually a study site, who see only their own records.

05The project lifecycle

Test first with fake data, then go live.

  • Development: everything can be changed. Build the forms and test them thoroughly with fake records. Never enter real participant data in a development project.[9]
  • Production: real data collection. Changes to forms now go through Draft Mode, so that existing data are not damaged by accident; Draft Preview Mode lets you test those changes first.[2][9]
  • Analysis / Cleanup: data collection has ended. Resolve queries, lock records and export.[9]
  • Completed: the project becomes a read-only archive.[9]

06The data dictionary and field types

Design the data dictionary first; it is also your codebook.

Every REDCap project is defined by a data dictionary: a table with one row per field. You can build it in the Online Designer, or write it in a spreadsheet, save it as CSV and upload it.[2] Because it lists every variable with its type, label, codes and validation, the data dictionary doubles as the codebook that your DMP asks for.[9]

Field types: the right type prevents errors

Text box

Short answers; add validation for date, number, integer, email or phone.

Notes box

Long free text. Use sparingly: free text is hard to analyse and may contain names.

Radio buttons

Choose exactly one option from a short list.

Drop-down

Choose one option from a long list.

Checkboxes

Choose all that apply. Each option becomes its own 0/1 variable.

Yes / No

Stored as 1 (yes) and 0 (no).

Calculated

Computed automatically from other fields, such as BMI or age.

Slider

A visual analogue scale from 0 to 100.

File upload / signature

Documents, images and e-signatures.

Always set

  • Minimum and maximum values for numbers and dates.
  • Required fields for key variables.
  • The identifier flag on every field that contains personal information (name, date of birth, phone, address), so it can be removed on export.
  • Missing data codes, so you can record why a value is missing.

From the course lecture.[9]

Use short, lower-case variable names without spaces (weight_kg, not Weight of patient), and put the unit in the name or label. Variable names are what you will type in R or Stata for the rest of the project.

07Branching logic, calculations and action tags

Show only relevant questions, compute values automatically, and fine-tune field behaviour.

Fields are referred to by their variable name in square brackets. The examples below come from the course lecture.[9]

Branching logic

A field with branching logic is shown only when its condition is true. This keeps forms short and prevents answers to questions that do not apply.

# show only if a lab evaluation was done
[lab_eval] = '1'

# women of reproductive age
[sex] = '2' and [age] >= 15 and [age] <= 49

# checkbox option 3 is ticked
[symptoms(3)] = '1'

# a value from another event (longitudinal projects)
[baseline_arm_1][hiv_status] = '1'

Calculated fields

# BMI, 1 decimal
round([weight_kg] / (([height_cm]/100)^2), 1)

# age in years at enrolment
rounddown(datediff([dob], [enrol_date], 'y'), 0)

# days since the last visit
datediff([last_visit], 'today', 'd')

Action tags

Action tags are added to a field to change how it behaves. Common ones:

Action tagWhat it does
@TODAYFills in today's date when the form is opened
@NOWFills in the current date and time
@HIDDENHides the field on the form
@READONLYShows the field but prevents editing
@DEFAULTPre-fills a default value

08Surveys and participants

Collect data directly from participants, online or offline.

Any instrument can also be used as a survey. First enable surveys for the project in Project Setup, then enable each instrument you want to use as a survey.[9]

Public link and QR code

One link for everyone: for open or anonymous recruitment.

Participant list

Personal invitations by email, with automated reminders.

e-Consent

Participants consent online; REDCap keeps a signed PDF copy with the consent version and date.

Alerts and notifications

Automatic messages, for example an email to the PI when a serious adverse event (SAE) is reported.

Multi-Language Management

One instrument, available in several languages.[2]

Mobile App and MyCap

Offline data collection by field staff (Mobile App), and a participant app for patient-reported outcomes (MyCap).

09Longitudinal studies

Events × instruments: what is collected when.

In a cohort or trial, the same participant is seen several times. In a longitudinal REDCap project you define the events (time points), then tick which instruments are collected at each event. Set it up via Project Setup → enable longitudinal data collection → define events → designate instruments.[9]

InstrumentBaselineWeek 4Month 3Month 6Month 12
Consent & enrolment✓
Demographics✓

✓ = collected at that event. ↻ = repeating instrument: can be filled in as many times as needed at an event, which suits adverse events or medications.[9] If participants are randomised to groups with different schedules, each group becomes an arm with its own events.

11Data quality

Prevent errors, detect them, then correct them with a trace.

1

Prevent

Field validation (types, ranges, required fields) and branching logic stop many errors at the moment of entry.

2

Detect

Data Quality rules: REDCap has built-in checks (for example missing values or values outside the range) and you can write your own. Missing data codes record why a value is missing.

Custom rule
Flag impossible combinations: [sex] = '1' and [pregnant] = '1'
3

Correct and trace

The Data Resolution Workflow lets monitors open queries, sites answer them, and data managers close them. Logging keeps a full audit trail, and records can be locked and e-signed once they are final.

From the course lecture.[9]

12Export and analysis

From REDCap to R, Stata, SPSS or Python, safely.

REDCap exports to CSV (raw codes or labels), R, Stata, SPSS and SAS, and to CDISC ODM (XML), together with a script that applies the variable and value labels.[2][9]

De-identify on export

  • Remove all fields tagged as identifiers.
  • Remove unvalidated free-text fields, which may contain names.
  • Shift all dates by a random number of days.
  • Replace the record ID with a hashed value.

Export options listed in the course lecture.[9]

A reproducible pipeline with the API

Instead of exporting by hand each time, you can read the data straight into R with the REDCapR package[6] (or into Python with PyCap[7]) through the REDCap API. Your analysis then always starts from the current data.

library(REDCapR)
tb <- redcap_read_oneshot(
  redcap_uri = "https://redcap.uantwerpen.be/api/",
  token      = Sys.getenv("REDCAP_TOKEN")
)$data

API tokens are passwords

An API token gives full access to the project with your rights. Keep it in your .Renviron file (read with Sys.getenv()), never in a script, on GitHub, in an email or in a chat with an AI tool.[9]

13REDCap and your Data Management Plan

Choosing REDCap answers several DMP questions at once.

If your group project uses REDCap, say so in your DMP and be specific. The table shows where REDCap fits into the six DMP sections from the DMP pre-class reading.[10]

DMP sectionWhat to write about REDCap
Data collectionData collected in a REDCap project with forms and surveys; longitudinal events; Mobile App for offline collection
Documentation & qualityData dictionary as codebook; validation, required fields, branching logic; Data Quality rules and query workflow
Storage & backupData on the institution's REDCap server, not on laptops; user rights; DAGs per site
Legal & ethicalIdentifier flags; e-consent with versioned PDF; audit trail; access limited to named people
Sharing & preservationDe-identified export to open formats (CSV + data dictionary) for deposit in a repository
ResponsibilitiesWho builds the project, who manages users, who runs quality checks, who exports

REDCap also supports UAntwerp's rules on sensitive data: use institutional services rather than external cloud tools, give access on a need-to-know basis, and document all processing of personal data.[11]

17Check yourself

A random practice quiz first, then a few open questions.

Practice quiz

Each round gives you 20 questions drawn at random, so every round is different. If you get one wrong, you see the right answer and why straight away. Score 14 or more (70%) to pass.

Question 1 of 20Score: 0

Open questions

Try to answer first, then open the answer.

1. Why should you never enter real participant data in a project in Development status?

Development is for building and testing; everything can still be changed, which can damage or delete data. Real data belong in Production, where changes go through Draft Mode.

2. Write branching logic that shows test_type only when a lab evaluation was done.

[lab_eval] = '1'. Because lab_eval is a Yes/No field, "yes" is stored as 1.

3. A multi-site study has three hospitals. How do you make sure each hospital sees only its own participants?

Create a Data Access Group (DAG) for each hospital and assign each user to their site's DAG. Users in a DAG see only the records of that DAG.

4. Name three ways to de-identify data on export.

Remove fields tagged as identifiers; remove unvalidated free text; shift dates; hash the record ID.

5. Where should your API token be kept, and why?

In your .Renviron file, read with Sys.getenv(). A token works like a password: anyone who has it can access the project with your rights.

18Glossary

Terms you will meet in REDCap.

EDC
Electronic data capture: software for collecting research data electronically, with validation, user rights and an audit trail.
Data dictionary
The table (CSV) that defines every field of a project: name, form, type, label, choices, validation and flags.
Online Designer
The REDCap screen for building instruments in the browser.
Branching logic
A condition that decides whether a field is shown.
Action tag
A code such as @TODAY or @HIDDEN that changes how a field behaves.
Repeating instrument
A form that can be filled in several times per record or event, such as adverse events.
Draft Mode
The way to change forms in a project that is in Production.
Data Resolution Workflow
REDCap's query system: open, respond to and close questions about data values.
Audit trail (logging)
A record of every change, with who made it and when.
API
Application programming interface: a way for software such as R or Python to read and write REDCap data directly.
MyCap
A participant app, connected to REDCap, for collecting patient-reported outcomes.
SAE
Serious adverse event: an event in a clinical study that must be reported quickly.
